# 多版本兼容

项目针对较新的 Bukkit/Paper API 编写，并通过注册表及反射处理部分版本差异。当前构建依赖为 `ink.ptms.core:v260100:260100`，Java 编译目标为 21。注册表探测不等于已验证所有 1.21.x、26.x 服务端；请先在目标服务端测试，并运行 `/sgem compat all` 检查实际能力。当前没有完整 Folia 适配验证。

---

## 实现原理：不猜版本，只问服务端

大多数插件用「如果版本 ≥ X 就支持 Y」的写法，问题是每出一个新版本都要更新插件，而且 Mojang 从 2026 年改用「年份.次版本」命名（26.1、26.2）后，版本号比较很容易出错。

SnowyGems 的做法是**启动时读服务端的注册表**，把当前实际存在的属性、附魔、药水效果、物品读成一份快照，之后所有查询都基于这份快照。

这带来三个直接好处：

::card-group
  :::card
  ---
  icon: i-lucide-zap
  title: 探测当前注册表
  ---
  通过注册表查找当前存在的属性、附魔和效果；是否可用仍取决于服务端 API 与对应奖励实现。
  :::

  :::card
  ---
  icon: i-lucide-shield-check
  title: 低版本优雅降级
  ---
  配置里写了当前版本没有的内容，只跳过那一条并记日志，其他宝石照常工作。
  :::

  :::card
  ---
  icon: i-lucide-package-plus
  title: 数据包内容也认
  ---
  你用数据包自定义的附魔/属性同样在注册表里，插件一样能识别。
  :::
::

## 查看当前版本支持什么

```
/sgem compat        # 简报
/sgem compat all    # 完整清单 + 配置自检明细
```

输出包含：

- 服务端实现与版本
- 注册表规模（属性/附魔/效果/物品各多少项）
- `AttributeModifier` 用的是新 API 还是旧 API
- 逐项能力探测结果（支持 / 当前版本没有 + 需要什么版本）
- 功能模块启停状态
- 配置自检结果

启动时也会打印简报，可以在 `config.yml` 里用 `Compat.ReportOnStartup: false` 关掉（仍可用命令随时查看）。

## 各版本新增内容一览

插件已把这些内容纳入探测清单，配置里可以直接写：

### 物品

| 内容 | 引入版本 | 配置里怎么写 |
| --- | --- | --- |
| 锤 MACE | 1.21 | `Require: [MACE]` |
| 矛 SPEAR | 1.21.11 | `Require: [SPEAR]`、`onAttack`/`onUse` 等近战触发 |
| 铜盔甲 / 铜工具 | 1.21.9 | `Require: [COPPER_*]` |
| 狼铠 WOLF_ARMOR | 1.20.5 | `Require: [WOLF_ARMOR]` |
| 刷子 BRUSH | 1.20 | `Require: [BRUSH]` |

::alert{icon="i-lucide-info"}
**矛是分材质命名的物品**，不存在单一的 `SPEAR` 材质——实际是 `WOODEN_SPEAR`、`STONE_SPEAR`、`COPPER_SPEAR`、`IRON_SPEAR`、`GOLDEN_SPEAR`、`DIAMOND_SPEAR`、`NETHERITE_SPEAR` 七种。配置里写分类关键字 `SPEAR` 即可匹配全部材质，不需要逐个列出；插件靠 `_SPEAR` 后缀识别，所以将来新增材质的矛也会自动纳入。

矛是近战武器，核心动作是突刺与蓄力攻击，因此落在 `WEAPON`、`MELEE`、`SPEAR` 三个分类里，不属于 `RANGED`，也不会作为 Projectile 触发 `onLaunch`/`onHit`。
::

## 旧名兼容

1.20.5 起 Mojang 把附魔、药水效果、属性都从静态常量改成了注册表，旧名（`DURABILITY`、`DAMAGE_RESISTANCE`、`GENERIC_MAX_HEALTH`）在新版本已经不存在。

插件内置了旧名 → 新键的映射表，**老配置不用改**：

| 你写的 | 实际解析成 |
| --- | --- |
| `DURABILITY` | `unbreaking` |
| `DAMAGE_ALL` | `sharpness` |
| `LOOT_BONUS_BLOCKS` | `fortune` |
| `ARROW_INFINITE` | `infinity` |
| `DAMAGE_RESISTANCE` | `resistance` |
| `FAST_DIGGING` | `haste` |
| `INCREASE_DAMAGE` | `strength` |
| `JUMP` | `jump_boost` |
| `GENERIC_MAX_HEALTH` | `max_health` |

三种写法都能用：项目简写（`health`）、现代注册表键（`max_health`、`minecraft:scale`）、旧 Bukkit 常量名（`GENERIC_MAX_HEALTH`）。

::alert{icon="i-lucide-lightbulb"}
新写配置建议直接用**现代注册表键**（小写下划线，如 `unbreaking`、`sharpness`、`resistance`），和游戏内 `/enchant`、`/effect` 的补全一致，不容易记错。
::

## 功能模块开关

`config.yml` 的 `Compat.Modules` 下有 7 个模块，每个可取三种值：

| 值 | 含义 |
| --- | --- |
| `auto` | 由服务端注册表决定：有就启用，没有就停用（**默认，推荐**） |
| `true` | 强制启用。注册表里没有时相关配置会报「跳过」 |
| `false` | 强制停用。即使服务端支持也不启用 |

| 模块 | 管辖内容 |
| --- | --- |
| `Mace` | 锤及其专属附魔（密度/穿透/风爆） |
| `Spear` | 矛（全部材质的分类匹配）与专属附魔「突进」`lunge`；攻击技能使用 `onAttack`/`onUse` 等通用标记 |
| `CopperEquipment` | 铜盔甲与铜工具纳入 ARMOR / TOOL 分类 |
| `ModernAttributes` | 1.20.5+ 新属性（scale、交互距离、重力等） |
| `MiningAttributes` | 1.21.2+ 挖掘与移动类属性 |
| `TrialEffects` | 1.21+ 试炼密室药水效果 |
| `WaypointAttributes` | 26.x 路径点属性 |

模块停用后，它管辖的属性/附魔/效果/物品在查询时一律返回「不存在」，上层按既有的「跳过并提示」路径处理。

::alert{icon="i-lucide-info"}
**平时不需要动这些开关。** `auto` 已经能正确处理绝大多数情况。手动改的场景只有一个：混服。
::

## 混服策略

如果你有多个不同版本的子服，共用同一份配置：

::steps
### 保持 `auto`（推荐）

什么都不用改。高版本子服自动启用新内容，低版本子服自动跳过。代价是低版本控制台会有「N 处内容当前版本不支持，已跳过」的提示。

### 低版本子服手动关掉高版本模块

如果嫌那条提示烦，在低版本子服的 `config.yml` 里把对应模块设为 `false`：

```yaml
Compat:
  Modules:
    Spear: false              # 这个子服是 1.21.4，没有矛
    WaypointAttributes: false # 也没有 26.x 的路径点属性
```

这样 `Require: [WEAPON]` 在这个子服上就不会把矛算进去，相应功能按模块配置跳过，配置自检可能记录版本相关提示。

### 上线前用 strict 自检

正式服上线前把 `OnMissingFeature` 改成 `strict`，重载一次，控制台会列出**真正写错**的条目并拒绝加载，修正后再重载。没有错误后可以继续使用 strict，也可改回 skip。
::

## 配置自检的两类问题

自检会区分两种情况，这个区分很重要：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| **版本不支持** | 1.21.4 上写了 `Require: [SPEAR]` | 正常状态，只记 Debug 日志 + 一行概要 |
| **写错了** | 写了 `Enchant{name=sharpnes}`（拼错） | 任何版本都不会生效，明确报出来 |

::alert{icon="i-lucide-lightbulb"}
不做这个区分的后果是：内置的新版本示例宝石会在 1.21.4 上刷出几十条「错误」，服主看几次就再也不看这个报告了——真正的拼写错误也就被淹没了。
::

判据是模块归属表：归某个版本模块管的键算「版本不支持」，其余算「写错了」。写错的条目会带上拼写建议（如「你是不是想写: sharpness」）。

`OnMissingFeature` 三个级别的差异**只影响「写错了」这一类**的输出方式：

| 级别 | 行为 |
| --- | --- |
| `skip` | 一行概要 + Debug 明细（默认） |
| `warn` | 用 WARNING 级别逐条输出 |
| `strict` | 用 SEVERE 逐条输出配置错误，并拒绝此次加载 |

`strict` 遇到配置错误会阻止本次加载：重载保留旧宝石、菜单、技能、配方与功能模块；首次启动失败会停用插件。语言和调试等全局设置不属于回退范围。文件加载异常、重复 ID、关键引用错误在任何级别下都会拒绝加载。单纯的版本能力缺失仍按 VERSION 类型处理。

## AttributeModifier 的 API 差异

这是插件里唯一真正需要按版本分支的地方，插件已经处理好，写在这里供参考：

| 版本 | 构造函数 |
| --- | --- |
| 1.20.4 及以前 | `AttributeModifier(UUID, String, double, Operation, EquipmentSlot)` |
| 1.20.5 起 | `AttributeModifier(NamespacedKey, double, Operation, EquipmentSlotGroup)` |
| 1.21.9 前后 | 部分服务端实现开始移除旧构造 |

插件优先用新 API，用反射探测可用性并缓存结果。清理旧修饰符时**同时按 NamespacedKey 和 UUID 两种身份匹配**——因为玩家的装备可能是在插件用旧 API 的版本上镶嵌的，服务器升级后如果只按新 key 清理，旧修饰符会永久残留并持续叠加。

`/sgem compat` 会显示当前用的是哪套 API。

`slot` 的槽位组语义（`any`、`armor`、`any_hand`）是 1.20.5+ 才有的。在只支持旧 API 的服务端上，这几个值会退化成主手。

## 常见问题

**升级服务端版本后要做什么？**

先备份并在测试服检查旧装备的镶嵌、技能和拆卸，再运行 `/sgem compat all` 确认能力识别。如果之前手动关过模块，可按需改回 `auto`。参见[升级与验收清单](/snowygems/upgrade)。

**降级服务端版本后呢？**

插件会跳过无法识别的高版本功能，但这不代表世界与高版本物品能安全降级。请使用目标版本可用的备份，在测试服核对配置和装备。按需把不使用的模块设为 `false`。

**为什么我的新属性宝石没效果？**

按顺序检查：

1. `/sgem compat all` 确认这个属性在你的版本上存在
2. 确认没有手动把对应模块设成 `false`
3. 检查 `limit` 和 `var` 是否**同号**（这是最常见的原因，见[宝石配置](/snowygems/gems)）
4. 先用 `/sgem debug` 开启调试，再用 `/sgem debug Reward` 选择标签，查看实际执行结果
